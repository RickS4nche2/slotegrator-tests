# BUG-007. Вопрос к требованиям: 400 или 401 для некорректного CredentialsDTO

## Краткое описание

Для `POST /api/tester/login` требуется уточнить [AUTH-05](../api-spec.md#auth-05): OpenAPI перечисляет 400 и 401, но не связывает каждый отказ с конкретным нарушением `CredentialsDTO`. Наблюдаемый 401 сам по себе не доказывает дефект платформы. **Классификация — вопрос к требованиям; xfail снят.**

## Оценка серьёзности и приоритета

Предлагаемая оценка, не утверждённая владельцем: **Severity — не назначена, дефект поведения не подтверждён; Priority — P2 для уточнения требований**. Решение нужно для однозначного ожидаемого результата и классификации ошибок клиента. Выдача токена при этих запросах не наблюдалась, поэтому оснований для приоритета инцидента безопасности здесь нет.

## Окружение

- Стенд: `https://testslotegrator.com`.
- Наблюдение в предыдущем прогоне: 2026-10-09, 14:06:12–14:08:08 +03:00 (Europe/Istanbul).
- Build/version/commit сервиса: **неизвестны**; источник версии развёртывания недоступен. `info.version: 1.0` в OpenAPI — версия документа, а не сборки backend.
- Источник требований: [сохранённый OpenAPI](../../src/test/resources/contracts/players-openapi.json), задание и [спецификация проекта](../api-spec.md).

Приведённые результаты относятся только к указанному прогону 9 октября 2026 года.

Итоговый прогон 9 октября 2026, 16:19–16:23 +03:00: все семь случаев отказа прошли уточнённую проверку 400/401 без токена. Это не подтверждает обязательность одного конкретного кода.

## Предусловия

Basic корректен. Каждый случай меняет одно поле допустимого исходного `CredentialsDTO`; остальные предпосылки сохраняются. Для случая короткого пароля действительным остаётся email тестера.

## Шаги воспроизведения

1. Для `email` по отдельности удалить поле, передать null и число.
2. Для `password` по отдельности удалить поле, передать null, число и строку длиной три.
3. Отправить семь независимых запросов с корректным Basic.
4. Зафиксировать фактический код и проверить отсутствие токена независимо от кода.

## Минимальный HTTP-запрос

Ниже случай `password:TOO_SHORT`. Значения в угловых скобках заменяются локально; Basic — Base64 от действительных имени и пароля. `abc` — намеренно короткий искусственный пароль, а не секрет тестера.

```http
POST /api/tester/login HTTP/1.1
Host: testslotegrator.com
Authorization: Basic <BASE64_BASIC_USERNAME_AND_PASSWORD>
Content-Type: application/json

{"email":"<TESTER_EMAIL>","password":"abc"}
```

Для воспроизведения каждого параметра используется отдельный запрос с полным JSON-телом из таблицы:

| Параметр теста | Тело запроса |
|---|---|
| `email:MISSING` | `{"password":"<TESTER_PASSWORD>"}` |
| `email:NULL` | `{"email":null,"password":"<TESTER_PASSWORD>"}` |
| `email:NUMBER` | `{"email":123,"password":"<TESTER_PASSWORD>"}` |
| `password:MISSING` | `{"email":"<TESTER_EMAIL>"}` |
| `password:NULL` | `{"email":"<TESTER_EMAIL>","password":null}` |
| `password:NUMBER` | `{"email":"<TESTER_EMAIL>","password":123}` |
| `password:TOO_SHORT` | `{"email":"<TESTER_EMAIL>","password":"abc"}` |

## Фактический результат

В предыдущем прогоне все **7 из 7** запросов получили **401**. Ответы содержали `statusCode` и `message`, без полей успешного токена. Создание игроков в этих случаях не выполнялось.

На момент этого прогона тест требовал только 400, поэтому все семь проверок завершились failed по коду. Это результат прежнего ожидания, а не доказательство, что любой из наблюдаемых 401 противоречит опубликованному контракту.

## Что известно и что требует решения

- **Известно из OpenAPI:** required, типы полей и минимальная длина пароля; для операции перечислены ответы 400 и 401.
- **Известно по прогону:** все семь запросов отклонены с 401, успешный токен отсутствовал.
- **Ранее предполагалось:** каждое нарушение структуры или длины обязательно должно возвращать 400. Явной таблицы такого соответствия в опубликованном контракте нет.
- **Требует решения владельца:** должен ли сервер отличать структурно недопустимые реквизиты от обычного отказа аутентификации и какими точными кодами.
- **Отдельно для TOO_SHORT:** короткая строка может быть обработана как неверный пароль с отказом 401. Само ограничение `minLength` не доказывает обязательность кода 400.

## Текущий ожидаемый результат

До уточнения принимаются документированные **400 или 401**, при обязательном отсутствии выданного токена. Тест продолжает выполняться без xfail. Ответ с токеном, неожиданный код либо непрозрачное тело, по которому нельзя проверить отсутствие токена, остаются ошибкой проверки.

Текст ошибки и дополнительные поля не нормируются: опубликованной схемы отказа нет.

## Влияние и рекомендация

Неоднозначность затрудняет построение точной обработки ошибок и ожидаемого результата теста. Подтверждённого успешного входа или повреждения данных в этих семи случаях нет.

Нужно согласовать таблицу причин отказа и кодов с владельцем API. После решения она должна одинаково отражаться в опубликованном контракте, спецификации и тестах. Изменять сервер только ради прежнего предположения о 400 оснований пока нет.

## Доказательства

- Тест: [TesterLoginIT#rejectsInvalidCredentials](../../src/test/java/qa/slotegrator/tests/integration/auth/TesterLoginIT.java), семь параметров из `invalidCredentials`.
- В прогоне 9 октября все семь случаев получили 401, успешный токен отсутствовал. Точные значения `message` здесь не приводятся, поскольку они не нужны для установленного факта и не являются нормативным ожиданием.

Очищенная выдержка из установленного результата, без домысливания текста ответа:

```text
POST /api/tester/login
cases: email MISSING/NULL/NUMBER; password MISSING/NULL/NUMBER/TOO_SHORT
all 7 HTTP statuses: 401
observed response keys: statusCode, message
successful token: absent
historical test expectation: 400
```

## Проверка после уточнения требований

- Зафиксировать решение владельца отдельно для структурных нарушений и короткого пароля.
- При требовании единственного кода уточнить ожидания соответствующих параметров и повторить их; прежний прогон не считать новым подтверждением.
- Сохранить проверки отсутствия токена, корректного входа и отказа при неверном структурно допустимом пароле.
- Не возвращать xfail без подтверждённого нарушения согласованного требования.
