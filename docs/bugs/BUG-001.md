# BUG-001. Успешный вход возвращает 201 вместо требуемого 200

## Краткое описание

`POST /api/tester/login` нарушает [AUTH-01](../api-spec.md#auth-01).

## Оценка серьёзности и приоритета

Предлагаемая оценка, не утверждённая владельцем: **Severity — Minor; Priority — P2**. Вход и выданный токен работают, но клиент с точной проверкой опубликованного кода отвергает результат. Исправление требуется для совместимости контракта.

## Окружение

- Стенд: `https://testslotegrator.com`.
- Воспроизведение: 2026-10-09, 14:06:12–14:08:08 +03:00 (Europe/Istanbul).
- Build/version/commit сервиса: **неизвестны**; источник версии развёртывания недоступен. `info.version: 1.0` в OpenAPI — версия документа, а не сборки backend.
- Источник требований: [сохранённый OpenAPI](../../src/test/resources/contracts/players-openapi.json), задание и явно принятые правила [спецификации](../api-spec.md).

Приведённые результаты относятся только к указанному прогону 9 октября 2026 года.

Повторный строгий прогон 9 октября 2026, 16:19–16:23 +03:00 подтвердил то же расхождение. Тесты выполнялись без преобразования падений в XFAIL; подготовка и резервная очистка завершились без ошибок.

## Предусловия

Действующие Basic-реквизиты и реквизиты тестера в локальной конфигурации. Тело соответствует `CredentialsDTO`.

## Шаги воспроизведения

1. Отправить POST входа с корректными Basic и JSON-реквизитами.
2. Сохранить исходный HTTP-код до разбора тела.

## Минимальный HTTP-запрос

Пример HTTP-запроса для повторения. Значения в угловых скобках необходимо заменить собственными реквизитами; Basic — это Base64 от пары `username:password`. Реальные пароли и токены в документ не включены.

```http
POST /api/tester/login HTTP/1.1
Host: testslotegrator.com
Authorization: Basic <BASE64_BASIC_USERNAME_AND_PASSWORD>
Content-Type: application/json

{"email":"<TESTER_EMAIL>","password":"<TESTER_PASSWORD>"}
```

## Фактический результат

Получен **201**. Контрактный тест воспроизвёл отклонение в одном из одного вызова; это не оценка частоты за другие периоды.

## Ожидаемый результат

Ровно **200**, как требуют задание и успешный ответ OpenAPI. Схема токена проверяется отдельно в [BUG-002](BUG-002.md).

## Влияние

Клиент, проверяющий документированный код, отвергает успешный вход. Функциональная работоспособность токена не устраняет несовместимость контракта.

## Технический анализ

- **Подтверждено:** успешный ответ стенда имеет код 201, контракт требует 200.
- **Неизвестно:** версия и серверная причина выбора кода.
- **Рекомендация:** привести успешный код операции к 200 и сохранить проверку тела отдельным тестом.

## Обходной путь

Подготовка функциональных тестов принимает опубликованный 200 и наблюдаемый 201. Контрактный тест и целевой E2E требуют 200; допуск подготовки не меняет приёмочное требование.

## Доказательства

- Тест: [PublishedLoginContractIT#loginStatusMatchesPublishedContract](../../src/test/java/qa/slotegrator/tests/contract/auth/PublishedLoginContractIT.java).
- Контрактная проверка на стенде завершилась failed: получен 201 вместо требуемого 200.

Минимальная очищенная выдержка; служебные поля и чувствительные значения опущены:

```text
POST /api/tester/login
expected status: 200
actual status:   201
```

Фрагмент ответа повторного прогона: HTTP **201**. Остальные поля опущены; токен скрыт, пример ID заменяет фактический идентификатор.

```json
{"accessToken": "[скрыто]"}
```

## Проверка исправления

- Повторить контрактный тест с валидными реквизитами: требуется 200.
- Проверить схему токена и его пригодность для защищённого запроса.
- После подтверждённого исправления снять привязанный xfail; неожиданный успех должен привлечь внимание, а не остаться скрытым.
