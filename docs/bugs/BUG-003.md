# BUG-003. Идентификатор игрока не соответствует PlayerResponseDTO

## Краткое описание

Ответы `create`, `getOne` и `deleteOne` нарушают [CREATE-02](../api-spec.md#create-02), [PROFILE-02](../api-spec.md#profile-02) и [DELETE-02](../api-spec.md#delete-02).

## Оценка серьёзности и приоритета

Предлагаемая оценка, не утверждённая владельцем: **Severity — Major; Priority — P2**. Расхождение затрагивает идентификацию ресурса в трёх операциях и документированный параметр удаления, поэтому влияет на совместимость клиентов, а не только на отображение поля.

## Окружение

- Стенд: `https://testslotegrator.com`.
- Контрактное воспроизведение: 2026-10-09, 14:17:44–14:17:52 +03:00 (Europe/Istanbul); отдельный предшествующий E2E — 13:36:35–13:36:57 +03:00.
- Build/version/commit сервиса: **неизвестны**; источник версии развёртывания недоступен. `info.version: 1.0` в OpenAPI — версия документа, а не сборки backend.
- Источник требований: [сохранённый OpenAPI](../../src/test/resources/contracts/players-openapi.json), задание и явно принятые правила [спецификации](../api-spec.md).

Приведённые результаты относятся только к указанному прогону 9 октября 2026 года.

Повторный строгий прогон 9 октября 2026, 16:19–16:23 +03:00 подтвердил то же расхождение. Тесты выполнялись без преобразования падений в XFAIL; подготовка и резервная очистка завершились без ошибок.

## Предусловия

Действующий Bearer; собственный новый игрок с уникальными email/username. Для наблюдения полного потока оснастка явно поддерживает строковый ID.

## Шаги воспроизведения

1. Создать собственного игрока валидным POST `create` и сохранить исходный JSON.
2. Запросить его профиль POST `getOne` по исходному email.
3. Удалить только этого игрока по подтверждённому ID; сохранить ответ и проверить отсутствие записи.
4. В каждом ответе сопоставить ключ и тип ID с исходной `PlayerResponseDTO`.

## Минимальный HTTP-запрос

Ниже последовательность HTTP-запросов для одной собственной записи. Все значения в угловых скобках нужно заменить; email и username должны быть уникальны для этого воспроизведения. ID удаления разрешено подставлять только после подтверждения, что запись соответствует исходным email и username. После удаления нужно проверить отсутствие этой записи в списке.

```http
POST /api/automationTask/create HTTP/1.1
Host: testslotegrator.com
Authorization: Bearer <ACCESS_TOKEN>
Content-Type: application/json

{"currency_code":"USD","email":"<UNIQUE_PLAYER_EMAIL>","name":"Проверка","password_change":"<VALID_PLAYER_PASSWORD>","password_repeat":"<VALID_PLAYER_PASSWORD>","surname":"Тест","username":"<UNIQUE_PLAYER_USERNAME>"}
```

```http
POST /api/automationTask/getOne HTTP/1.1
Host: testslotegrator.com
Authorization: Bearer <ACCESS_TOKEN>
Content-Type: application/json

{"email":"<UNIQUE_PLAYER_EMAIL>"}
```

```http
DELETE /api/automationTask/deleteOne/<OWN_CONFIRMED_PLAYER_ID> HTTP/1.1
Host: testslotegrator.com
Authorization: Bearer <ACCESS_TOKEN>
```

## Фактический результат

Три независимых контрактных метода воспроизвели дефект: в ответах создания и удаления обязательный `id` заменён строковым `_id`, в профиле `id` имеет строковый тип. Значение — 24 строчных hex-символа. Каждый метод завершился **failed по ожидаемому расхождению**, при отключённом xfail. Подготовка и резервная очистка прошли; последнее чтение списка каждого случая вернуло 200 и `[]`.

В предшествующем E2E то же расхождение наблюдалось во всех 12 созданиях, 12 профилях и 12 удалениях; сквозной поток с наблюдаемым адаптером завершился пустым списком.

## Ожидаемый результат

Каждый ответ соответствует `PlayerResponseDTO`: обязательный `id` типа `integer`, без замены на `_id` и без преобразования строк в числа. Отдельно OpenAPI задаёт path ID удаления как `integer/int32`; изменение публичной модели требует согласования всех её представлений.

## Влияние

Генерация клиента по OpenAPI даёт несовместимые модели ответа и параметра удаления. Один ресурс представлен разными именами поля в разных операциях.

## Технический анализ

- **Подтверждено:** различаются имя/тип ID в исходных ответах; сквозная идентичность строкового ID при этом сохранялась.
- **Неизвестно:** серверное устройство хранения и причина выбора формата; внешний вид ID не доказывает конкретную СУБД.
- **Рекомендация:** согласованно реализовать нормативный ID во всех операциях либо явно утвердить новую версию API и обновить её контракт. Одной смены DTO теста недостаточно.

## Обходной путь

Наблюдаемые модели `_id`/`id` со строковым значением позволяют готовить и очищать собственные данные. Поддержка текущего формата в оснастке не отменяет дефект контракта.

## Доказательства

- Сквозной сценарий [PlayersLifecycleE2EIT#completePlayersLifecycle](../../src/test/java/qa/slotegrator/tests/e2e/players/PlayersLifecycleE2EIT.java) подтвердил различие форматов create/getOne/deleteOne.
- Три метода [PublishedPlayersContractIT](../../src/test/java/qa/slotegrator/tests/contract/players/PublishedPlayersContractIT.java) выполнены с отключённым xfail и завершились failed:

| Метод | Время 2026-10-09, +03:00 |
|---|---|
| `profileMatchesPublishedSchema` | 14:17:44.431–14:17:46.663 |
| `deletionMatchesPublishedSchema` | 14:17:48.045–14:17:49.763 |
| `creationMatchesPublishedSchema` | 14:17:51.578–14:17:52.787 |

Подготовка и очистка прошли. Последний getAll в каждом случае вернул 200 и `[]`. В проверке delete цель удалена основным действием; повторное удаление при teardown не требовалось.

Минимальная очищенная выдержка; служебные поля и чувствительные значения опущены:

```text
create    → 201; key=_id, type=string, pattern=[0-9a-f]{24}; id absent
getOne    → 201; key=id,  type=string, pattern=[0-9a-f]{24}
deleteOne → 200; key=_id, type=string, pattern=[0-9a-f]{24}; id absent
expected PlayerResponseDTO: required id, type=integer
```

Фрагменты повторного прогона; остальные поля опущены, фактический ID заменён синтетическим значением той же формы:

Создание: HTTP **201**.

```json
{"_id": "0123456789abcdef01234567"}
```

Профиль: HTTP **201**.

```json
{"id": "0123456789abcdef01234567"}
```

Удаление: HTTP **200**.

```json
{"_id": "0123456789abcdef01234567"}
```

## Проверка исправления

- Выполнить все три контрактных метода на независимо подготовленных игроках.
- Проверить идентичность ID между create/getOne/getAll/deleteOne и сохранение исходных полей.
- Подтвердить адресное удаление цели, сохранение соседей и успешный резервный teardown.
