# BUG-008. Создание сохраняет игроков с нарушениями PlayerRequestDTO

## Краткое описание

`POST /api/automationTask/create` нарушает [CREATE-03](../api-spec.md#create-03) и отрицательные границы [CREATE-04](../api-spec.md#create-04).

## Оценка серьёзности и приоритета

Предлагаемая оценка, не утверждённая владельцем: **Severity — Major; Priority — P1**. Сервер сохраняет данные, запрещённые опубликованной схемой, включая значения ниже минимальной длины пароля. Нарушение целостности данных подтверждено чтением до очистки; дальнейшие последствия для других компонентов не установлены.

## Окружение

- Стенд: `https://testslotegrator.com`.
- Воспроизведение: 2026-10-09, 14:06:12–14:08:08 +03:00 (Europe/Istanbul).
- Build/version/commit сервиса: **неизвестны**; источник версии развёртывания недоступен. `info.version: 1.0` в OpenAPI — версия документа, а не сборки backend.
- Источник требований: [сохранённый OpenAPI](../../src/test/resources/contracts/players-openapi.json), задание и явно принятые правила [спецификации](../api-spec.md).

Приведённые результаты относятся только к указанному прогону 9 октября 2026 года.

Повторный строгий прогон 9 октября 2026, 16:19–16:23 +03:00: текущие 22 независимых негативных случая (21 параметризованный и совпадающая короткая пара) снова получили 201 и сохранили запись. Собственные записи удалены; ошибок очистки нет. Разница с историческими 25 ниже — удалённые дубли, а не исправление сервиса.

Контрольный прогон 19:02–19:07 +03:00 воспроизвёл расхождение во всех 22 независимых негативных случаях; резервная очистка удалила сохранённые записи.

## Предусловия

Действующий Bearer. Каждый случай имеет собственные уникальные данные, подтверждённого контрольного игрока и снимок до действия. Попытка регистрируется до POST, поэтому сохранённая вопреки отказу запись доступна резервной очистке.

## Шаги воспроизведения

1. Подготовить контрольного игрока и подтвердить исходное состояние.
2. Для каждого из семи полей независимо проверить отсутствие и null; для пяти полей, не являющихся паролями, — числовое значение. Оба пароля проверить одной одинаковой числовой парой. Это 20 структурных случаев; парная проверка подтверждает запрет числовой пары, а не независимую валидацию каждого пароля.
3. Отдельно проверить username длиной три и оба пароля одинаковыми строками длиной три. Всего — 22 случая.
4. После каждого POST прочитать состояние до teardown; затем очистить только собственные записи.

## Минимальный HTTP-запрос

Минимальный воспроизводимый пример — совпадающая пара `abc/abc`: оба пароля короче опубликованной границы четыре, поэтому несовпадение паролей исключено. Email и username заменяются уникальными значениями этого случая; Bearer — действующим токеном.

```http
POST /api/automationTask/create HTTP/1.1
Host: testslotegrator.com
Authorization: Bearer <ACCESS_TOKEN>
Content-Type: application/json

{"currency_code":"USD","email":"<UNIQUE_PLAYER_EMAIL>","name":"Проверка","password_change":"abc","password_repeat":"abc","surname":"Тест","username":"<UNIQUE_PLAYER_USERNAME>"}
```

После POST нужно прочитать список и сопоставить новую запись с исходными уникальными email и username. Сам код 201 ещё не доказывает сохранение:

```http
GET /api/automationTask/getAll HTTP/1.1
Host: testslotegrator.com
Authorization: Bearer <ACCESS_TOKEN>
```

Если запись сохранилась, после фиксации фактического результата удалить только её подтверждённый ID и собственные подготовленные данные, затем проверить их отсутствие. Очистка выполняется и при падении проверки:

```http
DELETE /api/automationTask/deleteOne/<OWN_CONFIRMED_PLAYER_ID> HTTP/1.1
Host: testslotegrator.com
Authorization: Bearer <ACCESS_TOKEN>
```

## Фактический результат

Все **25 из 25** негативных случаев получили **201** и сохранили новую запись: 24 параметризованных нарушения плюс одинаковые короткие пароли. Резервная очистка удалила созданные данные; в диагностическом прогоне ошибок cleanup нет, последние списки после очистки пусты. Эти успешные удаления не отменяют запрещённого сохранения до teardown.

## Ожидаемый результат

Ровно **400**, отсутствие новой записи и неизменность исходного состояния. Обязательность, типы и minLength заданы в OpenAPI; сопоставление нарушения с 400 и отсутствие побочного эффекта закреплены правилами проекта.

## Влияние

API принимает и сохраняет данные, которые его собственная схема объявляет недопустимыми. Клиенты могут получить записи с отсутствующими/неверно типизированными полями или длинами ниже границы. Дальнейшие бизнес-последствия в недоступных компонентах не проверялись.

## Технический анализ

- **Подтверждено:** недопустимые запросы возвращают 201 и имеют эффект сохранения. Проверка состояния сделана до очистки.
- **Рабочая гипотеза:** ограничения DTO могут не применяться к операции создания; конкретная серверная причина не установлена.
- **Рекомендация:** валидировать вход до сохранения и сохранять атомарность отказа. Проверить каждое ограничение отдельно, особенно совпадающую пару коротких паролей.

## Обходной путь

Предварительная клиентская валидация снижает риск для одного клиента, но не заменяет серверную. Оснастка находит и удаляет собственные ошибочно созданные записи; это восстановление стенда, а не успешный результат проверки.

## Доказательства

- Тесты: [PlayerCreationIT#rejectsInvalidPlayer и #rejectsMatchingShortPasswords](../../src/test/java/qa/slotegrator/tests/integration/players/PlayerCreationIT.java).
- На стенде воспроизведены 24 случая нарушения отдельного поля и один независимый случай совпадающих коротких паролей. Все проверки завершились failed; собственные записи удалены, ошибок очистки нет, итоговые списки пусты.

Минимальная очищенная выдержка; служебные поля и чувствительные значения опущены:

```text
request: both passwords are equal; each length=3 (minLength=4)
POST /api/automationTask/create → 201
new own record present before teardown: true
expected: 400; new record absent; original state unchanged
recovery: own records removed; cleanup errors=0
```

Фрагмент ответа повторного прогона: HTTP **201**. Остальные поля опущены; пример ID заменяет фактический идентификатор.

```json
{"_id": "0123456789abcdef01234567"}
```

## Проверка исправления

- Повторить актуальные 22 негативных случая: 21 параметризованный и один с совпадающей короткой парой. Три дублирующих случая прежнего набора из 25 удалены; проверка NUMBER задаёт одинаковые числовые значения обоих паролей. Ожидаются 400, отсутствие новой записи и сохранность прежних игроков и их полей.
- Проверить допустимую границу длины четыре для username и обоих паролей, а также обычное создание.
- Проверить, что диагностический отказ создания не становится зелёным из-за последующей очистки; teardown продолжает работать при любом падении.
