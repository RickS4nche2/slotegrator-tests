# BUG-006. Вход выдаёт токен без Basic и с неверным Basic

## Краткое описание

`POST /api/tester/login` нарушает [AUTH-04](../api-spec.md#auth-04).

## Оценка серьёзности и приоритета

Предлагаемая оценка, не утверждённая владельцем: **Severity — Major; Priority — P1, высокий приоритет безопасности**. Объявленный слой Basic не препятствует выдаче токена. Приоритет относится к нарушению этого слоя: обход JSON-пароля тестера или полный обход аутентификации не установлен.

## Окружение

- Стенд: `https://testslotegrator.com`.
- Воспроизведение: 2026-10-09, 14:06:12–14:08:08 +03:00 (Europe/Istanbul).
- Build/version/commit сервиса: **неизвестны**; источник версии развёртывания недоступен. `info.version: 1.0` в OpenAPI — версия документа, а не сборки backend.
- Источник требований: [сохранённый OpenAPI](../../src/test/resources/contracts/players-openapi.json), задание и явно принятые правила [спецификации](../api-spec.md).

Приведённые результаты относятся только к указанному прогону 9 октября 2026 года.

Повторный строгий прогон 9 октября 2026, 16:19–16:23 +03:00 подтвердил то же расхождение. Тесты выполнялись без преобразования падений в XFAIL; подготовка и резервная очистка завершились без ошибок.

Контрольный прогон 19:02–19:07 +03:00 воспроизвёл расхождение в обоих случаях Basic.

## Предусловия

JSON-реквизиты тестера корректны; никакой действующий Bearer не подмешивается. Проверяемые запросы отличаются только режимом Basic.

## Шаги воспроизведения

1. Отправить корректный `CredentialsDTO` без заголовка Authorization.
2. В независимом вызове отправить тот же допустимый класс тела с заведомо неверным Basic.
3. Проверить точный код и отсутствие токена в исходных ответах.

## Минимальный HTTP-запрос

Два независимых HTTP-запроса с корректными JSON-реквизитами. В первом заголовок Authorization отсутствует; второй содержит Base64 пары с действительным Basic-именем и заведомо неверным Basic-паролем. Действующий Bearer не добавляется. Значения в угловых скобках заменяются локально.

```http
POST /api/tester/login HTTP/1.1
Host: testslotegrator.com
Content-Type: application/json

{"email":"<TESTER_EMAIL>","password":"<TESTER_PASSWORD>"}
```

```http
POST /api/tester/login HTTP/1.1
Host: testslotegrator.com
Authorization: Basic <BASE64_BASIC_USERNAME_AND_WRONG_PASSWORD>
Content-Type: application/json

{"email":"<TESTER_EMAIL>","password":"<TESTER_PASSWORD>"}
```

## Фактический результат

В обоих случаях (**2 из 2**) получены **201** и непустой `accessToken`; корневые поля ответа — `user`, `accessToken`. Неверный JSON-пароль при корректном Basic в отдельном контрольном случае был отклонён.

## Ожидаемый результат

Ровно **401** и отсутствие успешного токена. Swagger объявляет Basic для операции; связь отсутствующих/неверных Basic с 401 явно закреплена правилом проекта. Наличие валидного JSON-пароля не заменяет обязательный Basic.

## Влияние

Объявленная дополнительная проверка Basic не применяется к входу. Это не доказательство обхода JSON-реквизитов или всех защищённых операций: такие выводы из этих запросов не следуют.

## Технический анализ

- **Подтверждено:** режимы MISSING и INVALID приводят к успешной выдаче токена при корректном теле.
- **Неизвестно:** на каком уровне отсутствует или иначе настроена Basic-проверка.
- **Рекомендация:** применять объявленную Basic-проверку до выдачи токена, сохраняя независимую проверку JSON-реквизитов.

## Обходной путь

Клиент не может заставить сервер отклонять чужой запрос. Для нормальных сценариев оснастка продолжает передавать действующий Basic; обходного пути, устраняющего нарушение, нет.

## Доказательства

- Тест: [TesterLoginIT#rejectsInvalidBasic](../../src/test/java/qa/slotegrator/tests/integration/auth/TesterLoginIT.java), параметры `MISSING`, `INVALID`.
- Оба случая воспроизведены на стенде: получен 201 с непустым accessToken вместо отказа 401 без токена.

Минимальная очищенная выдержка; служебные поля и чувствительные значения опущены:

```text
POST /api/tester/login
Basic=MISSING → 201; nonempty accessToken present
Basic=INVALID → 201; nonempty accessToken present
expected both: 401; token absent
```

Фрагмент ответа повторного прогона: HTTP **201**. Остальные поля опущены; значение токена скрыто.

```json
{"accessToken": "[скрыто]"}
```

## Проверка исправления

- Повторить оба режима с валидным телом; проверить 401 и отсутствие токена, в том числе вложенного.
- Сохранить успешный вход с правильными Basic/JSON и отказ при неправильном JSON-пароле.
- Не считать произвольное падение или непрозрачную ошибку доказательством исправления.
