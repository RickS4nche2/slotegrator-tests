# Спецификация Players API и требований к автотестам

Эта спецификация задаёт ожидаемое поведение пяти доступных операций и связь требований с тестами.
Расхождение реализации с требованием фиксируется как дефект; ожидаемый результат не выбирается по полученному ответу.
Устройство оснастки описано в [архитектуре](architecture.md), способы запуска — в [README](../README.md).

## Источники и приоритет требований

| Источник | Где зафиксирован | Как используется |
|---|---|---|
| Задание | [Задание](https://testslotegrator.com/automation), также `info.description` снимка OpenAPI | Обязательный результат целевого сценария |
| OpenAPI | [Исходный OpenAPI](../src/test/resources/contracts/players-openapi.json), полученный из [openapi.json](https://testslotegrator.com/assets/swagger/openapi.json) | Методы, авторизация, поля, типы и ограничения |
| Правило проекта | Явно принятые правила этого проекта | Уточнение неполных требований и инварианты целостности/доступа |
| Наблюдение | Наблюдаемая реализация стенда | Совместимость подготовки данных и очистки; самостоятельным источником нормы не служит |

Снимок описывает **Players API**, `info.version: 1.0`, OpenAPI **3.0.3**. `1.0` — версия описания, а не установленная версия сборки сервиса.
При конфликте продуктовых ожиданий применяется приоритет **задание → OpenAPI → правило проекта**. Противоречие не удаляется из исходного снимка.
Отдельные contract-тесты сохраняют проверку опубликованной документации, даже когда она противоречит выбранному продуктовому ожиданию.

- Для `getOne` выбирается **200 из задания**; указанный OpenAPI и возвращаемый стендом 201 остаётся расхождением.
- Для `getAll` требуется **список**; проект уточняет его представление как корневой JSON-массив. Одиночный объект в OpenAPI — дефект документации.
- Для ответа игрока сохраняется опубликованный **целочисленный `id`**. Строковый `id`/`_id` не объявляется новым нормативным типом.

## Адрес, авторизация и операции

Рабочий адрес задаётся через `BASE_URL`; используемый стенд — `https://testslotegrator.com`.
Документированные тела запросов и успешных ответов имеют формат `application/json`.
Реквизиты Basic, email/пароль тестера и полученный токен — разные входные данные; браузерный вход не заменяет API-вход.
Реальные значения в документацию и репозиторий не включаются.

| Метод и путь | Авторизация | Запрос | Выбранный успешный ответ | Основание |
|---|---|---|---|---|
| `POST /api/tester/login` | HTTP Basic | `CredentialsDTO` | **200**, `TokenDTO` | Задание, OpenAPI |
| `POST /api/automationTask/create` | Bearer | `PlayerRequestDTO` | **201**, `PlayerResponseDTO` | Задание, OpenAPI |
| `POST /api/automationTask/getOne` | Bearer | `PlayerRequestOneDTO` | **200**, `PlayerResponseDTO` | Код — задание, модель — OpenAPI; в OpenAPI код 201 |
| `GET /api/automationTask/getAll` | Bearer | Параметры не описаны | **200**, массив игроков | Код — OpenAPI, список — задание, массив — правило проекта |
| `DELETE /api/automationTask/deleteOne/{id}` | Bearer | Обязательный path `id` | **200**, `PlayerResponseDTO` | OpenAPI |

Профиль ищется **по email в JSON**, а не по ID. Удаляется игрок с ID, полученным при его создании.
OpenAPI задаёт path `id` как `integer/int32`; это ограничение отличается от реально используемого строкового идентификатора.
Для `getAll` нет документированных query-параметров сортировки или пагинации.

## Модели и ограничения

Все перечисленные ниже модели имеют корневой тип `object`. Имена JSON-полей сохраняются точно.
«Обязательно» означает наличие поля в `required`; отсутствие, `null` и значение другого типа — разные нарушения.

### Запрос входа — `CredentialsDTO`

| Поле | Тип | Обязательно | Ограничение OpenAPI |
|---|---|---|---|
| `email` | `string` | Да | `nullable: false`; `format` не указан |
| `password` | `string` | Да | `nullable: false`, `minLength: 4` |

### Ответ входа — `TokenDTO`

| Поле | Тип | Обязательно | Ожидание |
|---|---|---|---|
| `access_token` | `string` | Да | Непустой токен, пригодный для защищённого запроса; OpenAPI, задание, правило проекта |
| `token_type` | `string` | Да | Конкретное значение и enum не определены; OpenAPI |
| `expires_in` | `string` | Да | Именно строка; единицы и допустимые значения не определены; OpenAPI |
| `scope` | `string` | Да | Допустимые значения не определены; OpenAPI |

### Запрос создания — `PlayerRequestDTO`

| Поле | Тип | Обязательно | Ограничение OpenAPI |
|---|---|---|---|
| `currency_code` | `string` | Да | `nullable: false`; enum валют не указан |
| `email` | `string` | Да | `nullable: false`; формат и уникальность не заданы |
| `name` | `string` | Да | `nullable: false` |
| `password_change` | `string` | Да | `nullable: false`, `minLength: 4` |
| `password_repeat` | `string` | Да | `nullable: false`, `minLength: 4` |
| `surname` | `string` | Да | `nullable: false` |
| `username` | `string` | Да | `nullable: false`, `minLength: 4`; уникальность не задана |

Для позитивных случаев используется выбранная валюта **USD** и одинаковые значения обоих паролей.
Уникальные email/username позволяют отличить собственные данные; это мера изоляции, а не установленное бизнес-правило уникальности.
Граница паролей проверяется также парой одинаковых строк длиной 3, чтобы несовпадение паролей не подменяло проверку длины.

### Запрос профиля — `PlayerRequestOneDTO`

Единственное поле `email`: обязательная строка, `nullable: false`; формат email в схеме не задан.

### Ответ игрока — `PlayerResponseDTO`

| Поле | Тип OpenAPI | Обязательно | Примечание |
|---|---|---|---|
| `id` | `integer` | Да | В модели ответа диапазон и формат не указаны |
| `username` | `string` | Да | Значение исходного запроса сохраняется по правилу проекта |
| `email` | `string` | Да | Значение исходного запроса сохраняется по правилу проекта |
| `name` | `string` | Да | Значение исходного запроса сохраняется по правилу проекта |
| `surname` | `string` | Да | Значение исходного запроса сохраняется по правилу проекта |
| `currency_code` | **Не определён** | Да | Есть в `required`, отсутствует в `properties`; контракт проверяет наличие |

Для функциональных проверок правило проекта требует сохранять исходную строковую валюту вместе с остальными четырьмя полями.
`additionalProperties: false` не задан: дополнительные поля сами по себе не означают нарушение OpenAPI.
Запрет выдачи паролей нельзя выводить из отсутствия этих полей в `properties`; это потребовало бы отдельного требования и теста.
`CredentialsLoginDTO` опубликована, но ни одна из пяти операций её не использует.

## Принятые правила и инварианты

1. **Валидация игроков:** при корректной авторизации нарушение required/null/type/minLength переданного DTO возвращает ровно **400**. Это принятое правило проекта, а не исчерпывающая таблица причин из OpenAPI. Для `CredentialsDTO` приоритет валидации и проверки реквизитов не определён: ожидается отказ **400 или 401** без токена; выбор точного кода вынесен в [вопрос BUG-007](bugs/BUG-007.md).
2. **Авторизация:** отсутствующий/невалидный Basic или Bearer, а также неверный JSON-пароль тестера возвращают ровно **401**. Схемы авторизации и сам код опубликованы; выбранная связь причин с кодом — проекта.
3. **Отказ входа:** успешный токен не выдаётся. Проверяются `access_token`/`accessToken`, включая вложенные объекты. Непустой непрозрачный ответ означает невозможность доказать этот инвариант, а не успешную проверку.
4. **Создание:** успешный запрос создаёт ровно одну новую запись с новым ID. Пять значимых полей равны исходному запросу; остальные записи не меняются.
5. **Чтение:** профиль относится именно к запрошенной цели. Список содержит каждый собственный ID один раз, сохраняет одноимённых игроков; повторное чтение не меняет состав и поля.
6. **Удаление:** исчезает только указанная собственная цель. Остальные записи и их поля сохраняются; отсутствие подтверждается по ID/email/username.
7. **Отказ операции:** состояние до и после одинаково. Отказ создания не сохраняет запись даже при ошибочном HTTP-коде. Проверка выполняется **до teardown**.
8. **Неразглашение при отказе Bearer:** ответ не содержит известные ID/email/username, не переданные самим запросом. Каждый идентификатор проверяется отдельно; это не доказательство отсутствия любых персональных данных.
9. **Сортировка:** выполняется на клиенте по `name` по возрастанию `String.compareTo`, сохраняет полный набор записей и их поля. Порядок записей с равными именами не фиксируется. Для выбранных данных E2E эталон порядка имён задан вручную; повторная сортировка фактического ответа как oracle не используется.

OpenAPI перечисляет для входа ошибки 400/401, для игроков — 400/401/403, но не задаёт схемы ошибок и исчерпывающие причины.
Тесты не требуют конкретных сообщений или недокументированных полей ошибки.

## Наблюдения стенда и совместимость подготовки

| Операция | Наблюдение прогона 9 октября 2026 | Нормативное расхождение |
|---|---|---|
| login | 201, непустой строковый `accessToken` | [BUG-001](bugs/BUG-001.md), [BUG-002](bugs/BUG-002.md) |
| create | 201, строковый `_id` из 24 строчных hex-символов | [BUG-003](bugs/BUG-003.md) |
| getOne | 201, строковый `id` той же формы | [BUG-003](bugs/BUG-003.md), [BUG-004](bugs/BUG-004.md) |
| getAll | 200, корневой массив, строковые `id` | Ошибка схемы коллекции — [BUG-005](bugs/BUG-005.md); тип ID относится к [BUG-003](bugs/BUG-003.md) |
| deleteOne | 200, объект со строковым `_id` | [BUG-003](bugs/BUG-003.md) |

Подготовка допускает вход с 200 или 201 и ровно одним непустым строковым токеном `access_token`/`accessToken`. Для игроков распознаются опубликованный целочисленный ID и наблюдаемый ID из 24 hex-символов (`id` или `_id`); для функционального профиля допустимы 200/201. Эти допуски не меняют исходный JSON и не применяются к строгим проверкам контракта/E2E. Исправление сервиса на документированный формат не должно ломать другие тесты.

По умолчанию нарушения требований дают FAIL. Отдельный режим `-Dxfail.enabled=true` позволяет увидеть известные расхождения как XFAIL, представленный статусом skipped в JUnit/Allure. Пометка привязана к конкретному случаю и типизированной причине; другая ошибка и неожиданный успех не скрываются. Строгий E2E не имеет такой пометки. Неоднозначный [BUG-007](bugs/BUG-007.md) остаётся вопросом к требованиям; [BUG-004](bugs/BUG-004.md) фиксирует конфликт задания с OpenAPI.

## Независимость данных и границы покрытия

Каждый тест и параметризованный случай готовит собственную сессию, данные и журнал владения; предыдущие тесты не являются предусловием.
Состояние до действия подтверждается отдельно. Отказы и побочные изменения проверяются до резервной очистки.
Teardown выполняется после успеха, ошибки подготовки или проверки, удаляет только подтверждённые собственные записи и сохраняет первичную ошибку.
Endpoint-тесты допускают исходные записи и защищают их; последовательный запуск исключает конкуренцию самих тестов за снимок состояния.
Целевой E2E дополнительно требует пустой начальный и итоговый список; пустота сама по себе не доказывает изоляцию тестера от других пользователей стенда.

Следующие правила **не определены** и не подменяются предположениями:

- Приоритет валидации CredentialsDTO и проверки пароля, в том числе для строки короче четырёх символов.
- Коды для неизвестного email/ID и повторного удаления; 404 в опубликованной модели отсутствует.
- Бизнес-уникальность email/username, отказ при несовпадающих паролях, допустимый формат email и набор валют кроме выбранного USD.
- Непустота строк без `minLength`, дополнительные ограничения паролей, максимальные длины.
- Поведение при полном отсутствии тела: `requestBody.required` в трёх POST не задан; это отличается от отсутствия обязательного поля переданного объекта.
- Роли/403, доступ ко второму контролируемому тестеру, пагинация, серверная сортировка, лимиты и сроки ответа.
- Точный отказ на строковый ID неправильного формата; клиентская защита пути не является проверкой ответа сервера.

Сбой сети, подготовки или очистки и невозможность интерпретировать ответ отделяются от воспроизведённого нарушения требования API.
