# Соглашения о тестовом коде

Этот документ задаёт правила написания и сопровождения кода Slotegrator API Tests на Java, JUnit Jupiter, Feign, Rest Assured и Allure.

Связанные документы: [архитектура](architecture.md) описывает устройство проекта, [API-спецификация](api-spec.md) — требования и их привязку к тестам, [README](../README.md) — запуск. Эта конвенция определяет, как добавлять и изменять код.

Главное требование: по тесту и его отчёту понятны риск, подготовка, проверяемое действие и доказанный результат. Краткость сама по себе не служит целью; технические детали выделяются так, чтобы причинная история оставалась видимой.

## 1. Дизайн до реализации

Перед новым сценарием определяем:

- Требование или риск и источник ожидаемого поведения.
- Уровень проверки: локальная проверка оснастки, контракт, интеграционный API-тест или E2E-поток.
- Предпосылки, входные классы, границы и состояния; одно главное действие либо один связанный поток.
- Обязательные и запрещённые последствия, доступные наблюдения и условие завершения.
- Владение данными, резервную очистку и достаточный критерий покрытия.

Источник ожидаемого результата — [API-спецификация](api-spec.md): задание → непротиворечащий ему OpenAPI → явно принятые правила проекта. Наблюдаемая реализация описывает совместимость подготовки данных, но не меняет норму. Дефект связывается с нарушенным требованием; прежние тесты и примеры помогают понять дизайн, но не переопределяют требование. Не придумываем лимиты, коды, сообщения, роли или бизнес-правила; неопределённое поведение явно фиксируем в спецификации.

Для существенного поведения оцениваем классы эквивалентности, граничные значения, таблицы решений, переходы состояний, известные ошибки, комбинации факторов и метаморфные/дифференциальные проверки. В записи дизайна отмечаем применённые техники и причины неприменимости остальных. Проверяем nominal, invalid/missing, нижнюю/верхнюю границу, роли/состояния, повтор, необходимые и запрещённые эффекты, применимые concurrency/recovery.

Дизайн сохраняется кратко в матрице требований [API-спецификации](api-spec.md) и Javadoc теста: `Design:`, последовательность `Steps:` и наблюдаемые `Expected:`. Методы получают теги идентификаторов требований, например `@Tag("READ-01")`. Отложенные правила и границы покрытия отмечаем в спецификации; новый случай добавляем, когда он различает дополнительный риск, границу или состояние.

## 2. Читаемый сценарий и Allure

Обычная форма: **подготовка → действие → наблюдение → явная проверка результата и последствий**. Атомарной проверке достаточно одного точного verification-шага; искусственно дробить её не нужно. Обязательные шесть действий задания образуют один последовательный сценарий, дополнительные тесты независимы.

Шаги описывают предметное действие или точный результат: «Запросить профиль созданного игрока», «Отказ не изменил исходного игрока». Названия «Шаг 1», «Выполнить запрос», «Проверить результат» слишком общие.

Проверка выполняется **внутри** обещающего её `Allure.step`. Если шаг только читает список, он называется чтением. Финальные assertions после завершения verification-шага запрещены: такой отчёт показал бы успешную проверку до её фактического падения.

Не прячем весь сценарий в `runScenario()`, `execute(mode)` или универсальный helper. В тестовом методе остаются главные действия и вызовы предметных ожиданий. Транспорт, разбор JSON, генерация данных и техническая диагностика не загромождают эту историю.

Используем `Allure.step` и Runtime API без AspectJ. Человекочитаемые названия, Javadoc, сообщения и документация — на русском. Java-идентификаторы — на английском. Для сценарных классов задаём `@Epic`, `@Feature`, `@Story`, для методов — предметный `@DisplayName`.

## 3. Роли и структура

Один Maven-модуль, вся оснастка и тесты расположены в стандартном `src/test/java/qa/slotegrator`, зависимости имеют область `test`. Исполняемые проверки выделены отдельно от вспомогательного кода.

| Область | Ответственность |
|---|---|
| `api/client`, `api/model`, чистые классы контрактов в `api` | Feign, исходные HTTP-ответы, DTO и форма JSON |
| `expecteds` | Плоский набор предметных `*Expected.java`, без HTTP/cleanup |
| `helpers/auth`, `config`, `data`, `http`, `json`, `reporting` | Авторизация, конфигурация, данные и владение, транспорт и диагностика |
| `fixtures` | Локальные ответчики для self |
| `tests/self` | Локальные проверки оснастки по предметным подпакетам |
| `tests/contract` | Опубликованные HTTP-коды, схемы и обязательные поля |
| `tests/integration` | Поведение отдельных API-операций и последствия действий |
| `tests/e2e` | Сквозной API-поток; целевой сценарий задания с 12 игроками |

Тематические подпакеты `auth` и `players` создаются вместе с реальными проверками. Helpers, API и Expecteds не зависят от `tests` или `fixtures`; локальные проверки обращаются к оснастке через её явные публичные границы.

Тип проверки отражают пакеты `contract`, `integration`, `e2e` и соответствующие теги. Smoke и regression — пересекающиеся составы запуска через `@Tag("smoke")` / `@Tag("regression")`: копии классов и одноимённые каталоги запрещены. Критичный smoke-тест может также иметь тег regression.

Стандартный состав API-профиля — тег `api`. Дополнительный сценарий вводим только для риска, который существующие тесты не различают.

Локальные self-проверки называются `*Test` и запускаются Surefire без реквизитов стенда. API-классы называются `*IT` и запускаются Failsafe только в профиле `api-tests`. Пустой выбранный набор даёт ошибку сборки.

Имена отражают назначение: `PlayersExpected`, `AuthenticationExpected`, `PublishedContractExpected`, `PlayerProfileIT`, `CreationJournalTest`. Класс создаётся под реальную ответственность, а не заранее под каждую будущую ручку. Не создаём вложенные пакеты с единственным verification-файлом и общий `BaseApiTest` с накопленным состоянием.

**DRY и KISS:** выносим общий смысл, а не любое похожее выражение. Небольшое повторение читаемого сценария лучше универсального исполнителя со множеством флагов. Предпочитаем композицию: отдельный контекст объединяет сессию, генератор данных и журнал; узкое JUnit-расширение отвечает за lifecycle. Паттерн вводим под существующую ответственность или реальную вариативность, а не ради будущей гибкости.

Сервисные помощники остаются рядом со своей областью. Общий межсервисный уровень выделяем после появления хотя бы двух потребителей с одинаковыми типами и семантикой. Один и тот же бизнес-смысл, а не похожая форма кода, определяет переиспользование.

## 4. Ожидания в отдельных классах

Доменные проверки ответа, состояния и последствий выполняются в `*Expected.java`. В теле API-сценария вызываем, например, `PlayersExpected.verifyProfile(...)`, а не размещаем цепочки `assertEquals`, проверки JSON-полей и фильтрацию коллекций.

Ожидание получает факты и эталон явно: исходный HTTP-ответ, DTO, отправленный запрос, снимок до действия, снимок после действия, ожидаемый ID или код. Оно может разобрать данные чистым кодеком и использовать JUnit Assertions, но **не создаёт клиента, не авторизуется, не изменяет состояние, не выполняет polling или cleanup**. Наблюдение и ожидание по времени принадлежат явно названному helper.

Проверки формы и типов исходного JSON остаются отдельным чистым контрактным оракулом; `ApiContract` можно переиспользовать из предметных ожиданий. DTO не отправляют запросы и не содержат тестовые assertions.

Структурные проверки пригодности настроек, токена и владения ресурсом допустимы в оснастке: они защищают предусловия её работы. Они не заменяют явный продуктовый oracle. В небольших локальных проверках оснастки (`tests/self`) допустимы прямые JUnit assertions; предметные повторяемые ожидания всё равно переиспользуются. Не вводим оболочку вокруг каждого стандартного assertion ради одного переименования.

Сообщение ошибки объясняет различие, поле, ожидаемое и фактическое безопасное значение. Несколько независимых проверок можно объединить в `assertAll`; после проваленной структурной предпосылки нельзя продолжать небезопасные чтения полей. Ни сообщение, ни автоматический вывод аргументов не раскрывают секреты.

## 5. Независимый и различающий оракул

Ответ `2xx`, непустое тело или отсутствие исключения недостаточны. Для изменяющей операции определяем точный ответ, результирующее состояние, значимые взаимодействия/события и отсутствие запрещённых эффектов. Недоступные слои фиксируем как ограничение; доступ к внутренней БД и событиям Players API не выдумываем.

Создание и профиль сравниваем с **исходным запросом**, затем отдельно сверяем идентичность и согласованность create/getOne/getAll. Если сервис одинаково исказил имя во всех ответах, проверка должна упасть. Expected не вычисляется тем же проверяемым алгоритмом.

Снимок — данные для оракула. Коллекцию проверяем по составу, уникальности ID, значимым полям и, где требуется, порядку. Одинаковый размер не доказывает одинаковый состав; преобразование в `Set` не должно скрывать дубли. Сортировка сохраняет весь набор и проверяется по заранее выбранному правилу, а не только факту вызова сортировки.

Нормализация допустима только по контракту и сохраняет важные различия. Разбор DTO не подменяет проверку наличия полей и типов в исходном JSON. Дополнительные поля разрешены исходной схемой; неизвестный тип не превращается автоматически в предположительный `string`.

## 6. Функциональность и опубликованный контракт

Три уровня имеют разные задачи:

- **Integration:** проверяет поведение отдельной операции, исходные данные и побочные эффекты. Подготовка совместима с документированной и явно описанной наблюдаемой формой ответа; исправление сервиса не должно ломать её.
- **Contract:** проверяет исходные HTTP-коды, обязательные поля и типы без преобразования JSON.
- **E2E:** выполняет шесть шагов задания с точными кодами и схемами ответов игроков, включая самостоятельный шаг удаления и проверку его результата.

Произвольный `2xx` не принимается. Допуски подготовки перечислены в спецификации и не переносятся в продуктовый оракул. Отсутствующие поля не подставляются; опубликованная модель и наблюдаемая форма разделены явно. Проверяем статус до разбора тела: например, 502 с HTML должен сообщать об ошибочном HTTP-коде.

Теги различают общий `api`, уровни `contract` / `integration` / `e2e`, составы `smoke` / `regression`. Локальные проверки называются `*Test`, стендовые — `*IT`. Surefire исключает `api` независимо от имени выбранного класса.

По умолчанию известное нарушение остаётся FAIL. Для отдельного разбора известных дефектов доступен `-Dxfail.enabled=true`. Аннотация `@ExpectedFailure` связывает конкретный метод или точные `caseId` с `BUG-NNN`, Markdown и типизированной причиной. Текст сообщения и имена методов в стеке не используются. Тест и очистка выполняются; XFAIL представлен как `skipped` с меткой и описанием бага, неожиданный успех XPASS проваливает сборку. Целевой E2E не переводится в XFAIL.

До известного сбоя проверяем независимые инварианты: корректную форму успешного токена, обязательные поля игрока, сохранность исходных записей. Другая причина, несколько новых записей вместо одной, ошибка подготовки, сети или очистки не скрываются. Неоднозначность требований сначала уточняем; её нельзя объявлять подтверждённым дефектом. Пометку снимаем после проверки исправления и последствий.

## 7. Данные, именование и зависимости

Используем типизированные DTO и `record` для связанных параметров, а не несвязанные `Object[]` или `Map<String, Object>` в обычных сценариях. Снимки неизменяемы либо защищают вложенные изменяемые значения копиями. Secret-bearing DTO имеют безопасный `toString`.

Таймауты, окна стабильности, повторы, ограничения, ожидаемые количества и границы имеют предметные имена. Для времени используем `Duration`; в имени числа указываем единицу при необходимости. Адрес, реквизиты и выбранная валюта находятся в конфигурации. Инварианты задания, например 12 игроков, не становятся переключателем окружения, позволяющим незаметно ослабить тест.

Однотипные случаи задаём именованной коллекцией типизированных case-record или enum со стабильным безопасным `id`. Используем JUnit parameterization, `@MethodSource` или `@EnumSource`; новый представитель класса добавляется без копирования тела теста. Разные подготовка, главное действие или oracle требуют отдельных сценариев. Для намеренно некорректного DTO допустим исходный `ObjectNode`: изменение отдельного поля остаётся видимым. Пароль, токен и полный запрос не используются как имя или вывод параметра.

Все зависимости импортируются явно в начале файла. Wildcard-импорты, включая `Assertions.*`, и module-импорты запрещены. Не маскируем зависимость полными именами классов внутри методов без реального конфликта имён. Группы: Java/JDK → внешние библиотеки → проектные классы; явные static imports отдельной последней группой. Отступ — 4 пробела, ориентир строки — 120 символов. Точное оформление и версии закреплены в [pom.xml](../pom.xml) и [Eclipse formatter](../config/eclipse-formatter.xml); длинные литералы и комментарии не ограничены жёстким лимитом.

При изменении Java-кода приводим формат к общему стилю через `./mvnw spotless:apply`. Обычная сборка проверяет стиль в `validate` без изменения исходников; `./mvnw validate` даёт быструю отдельную проверку. Форматирование применяется ко всему `src/test/java`; комментарии/Javadoc и порядок членов класса автоматически не перестраиваются. `.editorconfig` задаёт базовые параметры редактора, Maven-профиль — воспроизводимый результат.

Метод и класс называются по поведению; названия `test1`, `execute`, `doEverything` не объясняют цель. Документируем смысл, предпосылки, границы и нестандартные решения, а не пересказываем каждую строку кода. При рефакторинге сохраняем test identity, параметры и метаданные либо обозначаем их намеренное изменение.

## 8. Предпосылки, изоляция и очистка

Подготовка не доказывает своё выполнение: перед главным действием перечитываем и проверяем значимое состояние. Если разные причины дают один код отказа, изолируем проверяемую причину входами и подтверждёнными предпосылками. Пустые или одинаковые данные, при которых дефект не отличим от правильного поведения, не дают убедительного PASS.

Каждый API-тест, включая отдельный параметризованный вызов, получает собственную сессию и необходимые для него данные. Для создания игроков дополнительно используются собственный UUID и журнал владения; проверке только входа такой журнал не нужен. Поиск идёт по своим точным признакам и ID. Не берём первого подходящего игрока, не переиспользуем существующего молча и не удаляем чужое. Токен и журнал не глобальные. Клиенты предоставляются через штатный JUnit lifecycle; конструкторы и статическая инициализация не выполняют HTTP. Общий ресурс имеет явные границы и причину использования.

Один тестер и пустой начальный список не доказывают scope `getAll`. Для проверки полностью пустого итогового списка предпочтителен подтверждённый контролируемый контекст. Отдельно разрешённый пользователем ограниченный прогон с неизвестным scope допускается с флагом `e2e.authorized=true`: начальная пустота, точный состав и защита собственного владения сохраняются, а неподтверждённая изоляция явно записывается в результат. Сам по себе пустой список не разрешает такой режим. Параллельный запуск на стенде отключён; изоляцию нельзя заменить порядком тестов или настройкой исполнителя.

Попытка создания регистрируется до запроса, подтверждённое владение ID — до последующих продуктовых assertions. Учитываем фактически созданные записи при неверном статусе, повреждённом или потерянном ответе. Исходную запись нельзя считать новой только по совпавшему email.

Резервная очистка находится в lifecycle (`AutoCloseable`/JUnit hooks) и работает при частичной подготовке и падении. API-метод не оборачиваем целиком в технический `try/catch` или `try-with-resources`: подключаем узкое JUnit-расширение по композиции. `AfterEachCallback` закрывает существующий контекст, не создавая его лениво; ошибка закрытия повторно выбрасывается для штатной агрегации Jupiter. Исходная assertion сохраняется первичной, новая ошибка cleanup повышает abort до неуспешного исхода. Диагностика сохраняет тип итоговой ошибки без исходного чувствительного сообщения. Проверяемое удаление из задания остаётся явным бизнес-шагом; оно не заменяет резервную очистку. Очистка проверяет владение, продолжает остальные независимые удаления после ошибки, подтверждает итог чтением и сохраняет исходную ошибку вместе со всеми ошибками/неразрешёнными ID. Неясное владение даёт явную проблему, а не удаление наугад.

## 9. Негативные проверки и ожидание по времени

До резервной очистки проверяем последствия отказа: отклонённое создание не добавило запись; исходные записи и их поля сохранены; отклонённое удаление сохранило игрока. Успешная очистка не исправляет исходный FAIL.

Для синхронного эффекта свежий снимок после ответа допустим, если семантика завершения подтверждена. Для асинхронного требуется наблюдаемое условие завершения и повторные проверки в течение полного именованного окна стабильности. Произвольный `sleep` с одной выборкой не доказывает отсутствие эффекта. Если завершение/видимость неизвестны, фиксируем ограничение вместо уверенного PASS.

Транспорт не повторяет изменяющую команду ради успешного результата, редирект не скрывает исходный код. Повтор команды разрешён только как явно проверяемое действие отдельного сценария. Polling повторяет чтения с deadline; не повторяем весь тест, чтобы замаскировать первое нарушение состояния.

## 10. Пример из действующего теста

Фрагмент [PlayerDeletionIT](../src/test/java/qa/slotegrator/tests/integration/players/PlayerDeletionIT.java) показывает штатную подготовку, композицию lifecycle, собственную цель и контрольного соседа, наблюдение до очистки и ожидания в отдельном классе. Опущены только импорты и другие методы класса.

```java
/** Независимые проверки адресного удаления; последствия проверяются до резервной очистки. */
@Epic("Players API")
@Feature("Удаление игрока")
@Story("Удаление затрагивает только собственную цель и требует авторизации")
@Tag("api")
@Tag("integration")
@Tag("regression")
@DisplayName("Независимые проверки удаления игрока")
class PlayerDeletionIT {
    private PlayersTestContext context;

    @RegisterExtension
    final PlayersLifecycleExtension lifecycle = new PlayersLifecycleExtension(() -> context);

    @BeforeEach
    void prepareIndependentContext() {
        context = new PlayersTestContext(ProjectSettings.load());
        Allure.step("Получить и проверить токен собственного контекста",
                () -> context.authenticate(context.login()));
    }

    /**
     * Design: переход существующей цели в отсутствие; сосед различает удаление лишних записей.
     * Steps: создать и подтвердить двух игроков, удалить цель, прочитать состояние до teardown.
     * Expected: 200 и _id цели; цель отсутствует по ID/email/username, остальные записи неизменны.
     */
    @Test
    @Tag("smoke")
    @DisplayName("Удаление убирает только целевого игрока и сохраняет контрольного соседа")
    @Tag("DELETE-01")
    void deletesOnlyOwnTarget() {
        var neighbour = context.preparePlayer("Контрольный");
        var target = context.preparePlayer("Целевой");
        var before = Allure.step("Прочитать исходное состояние перед удалением",
                () -> context.snapshot());
        Allure.step("Подтвердить существование цели и контрольного игрока перед удалением",
                () -> PlayersExpected.verifyOwnPlayers(before, List.of(target, neighbour)));

        var response = Allure.step("Удалить только подтверждённого целевого игрока",
                () -> context.delete(target, AuthorizationMode.VALID));
        var after = Allure.step("Прочитать состояние после удаления до резервной очистки",
                () -> context.snapshot());
        Allure.step("DELETE вернул HTTP 200 и удалил только цель, сохранив контрольного игрока",
                () -> PlayersExpected.verifyDeleted(response, target, before, after, context.codec()));
    }
}
```

Положительный ответ здесь проверяется вместе с изменением состояния. Цель создаётся второй, поэтому удаление самой старой записи не сможет пройти проверку; резервная очистка выполняется отдельно после продуктовой проверки.

## 11. Проверка изменений и ревью

Изменение сопровождается проверками, соответствующими его риску, и ревью. После исправления замечания повторяем проверку конкретного контрпримера и актуализируем связанную документацию.

На ревью оцениваем:

1. Архитектура и читаемость: видимый сценарий, границы клиентов/helpers/expecteds, DRY/KISS, метаданные.
2. Оракулы и покрытие: источник ожиданий, контрпримеры, границы, обязательные/запрещённые эффекты, пригодность данных.
3. Надёжность и диагностика: владение, частичный успех, очистка, транспорт, маскирование и достоверность отчёта.

Конкретное замечание содержит файл/строку, условие возникновения, неверное поведение и влияние. Для документа указываем противоречие правил или неоднозначное требование.

Зелёный общий прогон не закрывает конкретную претензию к oracle. Замечание считается исправленным после адресной перепроверки; ограничения и непроверенные случаи указываем явно.

Используем Maven/JUnit и Allure, без отдельного runner или парсера поверх них. Проверяем от дешёвого к дорогому: компиляция → настроенные статические проверки → минимальный релевантный локальный набор → разрешённый прогон стенда. Добавляем тесты под существенный риск, а не для каждой обратимой правки документа. Результаты компиляции, локального ответчика и живого API не смешиваем.

Секреты не попадают в Git, имена случаев, параметры, `toString`, исключения и вложения. Маскирование происходит до Allure, охватывает тела/заголовки и отражения; небезопасно разбираемое тело пропускается. Email скрывается независимо от имени поля, включая `createBy`. Изменение диагностики проверяем реальным файлом результата с искусственными маркерами, а не только возвратом функции.

Нативный lifecycle проверяется в `tests/self`: локальные Jupiter-фикстуры используют искусственные данные, loopback и отдельные каталоги Allure. Дочерний процесс принимает только фиксированные сценарии; намеренные failed/broken не смешиваются с основным отчётом. Низкоуровневые `try-with-resources` в проверках потоков, HTTP-ответчиков и `AutoCloseable` допустимы: запрет относится к технической обвязке целого API-сценария.
