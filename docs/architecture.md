# Архитектура тестового проекта

Проект проверяет Players API: авторизацию тестера, создание, чтение и удаление игроков, а также целевой сквозной сценарий задания. Источник ожидаемого поведения — [спецификация API и привязка требований к тестам](api-spec.md); подтверждённые отклонения описаны в [реестре дефектов](bugs/).

Подробные правила написания и ревью кода находятся в [код-конвенции](code-convention.md): читаемость шагов, отдельные ожидания, дизайн случаев, DRY/KISS, данные и очистка. Здесь описаны устройство проекта и границы ответственности компонентов.

## Основа и запуск

Один Maven-модуль на Java 25 с Maven Wrapper. Оснастка и тесты расположены в стандартном `src/test/java/qa/slotegrator`; зависимости имеют область `test`. Отдельный прикладной модуль и Spring для этой задачи не нужны.

JUnit Jupiter управляет тестами и их жизненным циклом. Surefire запускает локальные `*Test` и исключает тег `api`, в том числе при ручном `-Dtest=…IT`. Failsafe запускает API-классы `*IT` только с профилем `api-tests`. Пустой выбранный набор завершает сборку ошибкой. Выполнение последовательное.

Spotless проверяет форматирование на стадии Maven `validate`; явный `spotless:apply` приводит код к единому стилю. Параметры редактора заданы в `.editorconfig`, версии зависимостей и плагинов закреплены в `pom.xml`.

## Структура и ответственность

| Пакет | Назначение |
|---|---|
| `api/client`, `api/model`, контракты в `api` | Feign-интерфейсы, маршруты, DTO и проверки формы исходного JSON |
| `expecteds` | Предметные ожидания ответа и состояния: `AuthenticationExpected`, `PlayersExpected`, `PublishedContractExpected` |
| `helpers/auth`, `helpers/config` | Настройки и авторизация отдельной сессии |
| `helpers/data` | Подготовка данных, журнал владения и резервная очистка |
| `helpers/http`, `helpers/json`, `helpers/reporting` | Транспорт, строгий разбор JSON, безопасные вложения Allure, известные дефекты и сверка отклонений E2E |
| `fixtures` | Управляемые локальные ответчики и окружение самопроверок |
| `tests/self` | Локальные проверки оснастки без реквизитов стенда |
| `tests/contract` | Соответствие нормативным HTTP-кодам, полям и схемам |
| `tests/integration` | Независимые проверки отдельных API-операций и их последствий |
| `tests/e2e` | Целевой связанный поток задания с 12 игроками |

Тематические подпакеты, например `auth` и `players`, разделяют области API. Пакеты `api`, `helpers` и `expecteds` не зависят от исполняемых тестов или локальных ответчиков.

Уровни проверки отражают пакеты и теги `contract`, `integration`, `e2e`. `smoke` и `regression` — пересекающиеся составы запуска, а не копии тестов или каталоги. Стандартный состав API-профиля — `api`.

## HTTP-клиенты и данные

**Feign** описывает вспомогательные операции интерфейсами: получение токена, снимков списка и удаление при очистке. Возвращается исходный HTTP-ответ, поэтому код ошибки не теряется при десериализации.

**Rest Assured** выполняет проверяемые действия E2E (вход, создание, профиль, список, удаление, итоговое чтение), действия с игроками и отрицательные запросы авторизации. Feign используется для подготовки и наблюдения: предусловие пустого списка E2E, свежая проверка владения перед каждым DELETE, резервная очистка. Два контрактных теста входа дополнительно проверяют исходный Feign-ответ; проверка пригодности токена также читает список через Feign. Спецификация запроса задаёт транспорт и реквизиты; бизнес-ожидания находятся в `expecteds`.

Клиенты используют общие маршруты, DTO, `HttpResult` и `JsonCodec`; второй полный слой обёрток над каждой ручкой не создаётся. Feign использует Apache HttpClient с отключёнными повторами, редиректами и cookie. У Rest Assured повторы и редиректы также отключены; отказ соединения не повторяет DELETE. Глобальные настройки `RestAssured` не меняются.

**Jackson 3** строго разбирает типы, обязательные поля и дубли ключей. DTO не заменяют проверки исходного JSON: отдельно проверяются наличие полей, их типы и форма корня. Дополнительные поля допускаются там, где нормативная схема их не запрещает.

`ProjectSettings` загружает UTF-8-конфигурацию; переменные окружения имеют приоритет над локальным файлом. Секреты не хранятся в отслеживаемых файлах. Создание `ApiSession` не отправляет HTTP; вход выполняется явно, токен принадлежит конкретной сессии.

## Читаемый тест и точный оракул

Тест показывает причинную последовательность: **подготовка → действие → наблюдение → проверка результата и последствий**. Главные действия остаются в методе теста; транспорт, генерация данных и техническая диагностика вынесены в помощники.

Имена Allure-шагов описывают предметное действие или проверяемое свойство. Assertion выполняется внутри шага, который обещает эту проверку. В Javadoc фиксируются `Design`, `Steps`, `Expected`; названия, сообщения и пояснения пишутся по-русски, Java-идентификаторы — по-английски.

Предметные проверки вынесены в `*Expected.java`. Они получают факты и эталон явно: исходный запрос, HTTP-ответ, ожидаемый ID, снимки до и после действия. Ожидания не выполняют HTTP, подготовку, ожидание по времени или очистку. В локальных самопроверках допустимы прямые JUnit assertions.

Оракул различает правильное и ошибочное поведение:

- Успешный статус проверяется точно; произвольный `2xx` не принимается.
- Поля сравниваются с исходным запросом, а не только с другим ответом того же сервиса.
- Список проверяется по составу, уникальности ID и значимым полям; размер или `Set` сами по себе не доказывают корректность.
- Создание добавляет ровно одну запись и сохраняет прежнее состояние; удаление затрагивает только цель.
- Отклонённый запрос не должен изменить состояние или раскрыть чужие идентификаторы сверх переданных в запросе.
- Подготовка подтверждается чтением перед главным действием; последствия проверяются до teardown.

Однотипные входы задаются именованными параметризованными случаями. Проверяемые границы изолируются: например, два одинаковых коротких пароля отделяют нарушение длины от несовпадения пары.

## Требования и совместимость со стендом

Спецификация отделяет нормативные требования от наблюдаемой реализации и фиксирует связь с тестами. Текущее поведение сервиса не становится требованием только потому, что оно воспроизводится.

Целевой E2E проходит все шесть шагов задания. Поля запросов, адресность действий, сортировка и итоговая пустота — блокирующие проверки: их нарушение прерывает сценарий. Коды задания (вход и профиль — 200) и исходные схемы TokenDTO и PlayerResponseDTO проверяются через `ContractDeviations`: каждое отклонение отмечается упавшим вложенным шагом, а последний шаг «Сверить коды и схемы ответов с заданием и OpenAPI» проваливает тест со списком отклонений и номерами известных багов. Удаление — явный шаг Rest Assured от середины списка к краям с проверкой ID ответа и оставшихся записей: ошибочное удаление самой старой или самой новой записи вместо цели обнаруживается. Подтверждённый пустой итог закрывает журнал без резервных DELETE; при падении резервная очистка выполняется отдельно.

Подготовка endpoint-тестов принимает пригодные формы входа: 200/201 и один непустой токен `access_token` или `accessToken`. Адаптер игрока понимает документированный целочисленный ID и наблюдаемый строковый ID из 24 hex-символов. Это позволяет проверять бизнес-инварианты до исправления контракта и после него. Исходный JSON не переписывается; contract-тесты и E2E проверяют нормативные статусы и типы отдельно. Исправление 201 на 200 не ломает подготовку других случаев.

По умолчанию любое нарушение проваливает сборку. Дополнительный режим `-Dxfail.enabled=true` распознаёт только конкретный известный дефект, связанный с тестом и Markdown в `docs/bugs`. Оракул выбрасывает типизированную ошибку после проверки независимых инвариантов; расширение сравнивает её тип и причину, без анализа текста сообщения или stack trace. XFAIL показывается как skipped, XPASS проваливает сборку. Подготовка, очистка, неизвестные и составные ошибки не превращаются в XFAIL. Ссылка на баг прикладывается только при точном воспроизведении. Целевой E2E не использует XFAIL: известные расхождения в нём остаются падением итоговой сверки.

## Независимость и очистка

Каждый API-тест, включая отдельный параметризованный вызов, получает собственную сессию и необходимые данные. Тесты, создающие игроков, дополнительно используют собственный UUID и журнал владения. Тесты не вызывают друг друга, не используют глобальный токен и не зависят от порядка запуска.

`PlayersTestContext` объединяет необходимые компоненты через композицию. `PlayersLifecycleExtension` закрывает существующий контекст после каждого теста, в том числе при падении. Поэтому в API-тесте нет технической оболочки `try/catch`; исходную ошибку и ошибку очистки сохраняет JUnit lifecycle.

`CreationJournal` регистрирует попытку **до POST** и сверяет фактическое состояние независимо от кода ответа. Принадлежность записи доказывают уникальные признаки попытки и отсутствие ID в исходном снимке. Поэтому запись, сохранённая несмотря на ответ с ошибкой, тоже может быть найдена и удалена.

Перед каждым DELETE принадлежность проверяется заново. Исходные и неподтверждённые записи не удаляются. Чтение списка при очистке повторяется до трёх раз: кратковременный сбой не оставляет записей на стенде. Очередь удаления пересобирается до трёх проходов: собственный ID, впервые найденный свежим чтением (например, после потерянного ответа POST), тоже удаляется; решение по каждому ID принимается один раз. Ошибка общего чтения не запрещает последующие свежие проверки владения. Ошибка одного удаления не прерывает остальные. Итог определяет последний снимок: если он недоступен или в нём остались собственные либо неподтверждённые записи, `CleanupFailure` сохраняет совокупность ошибок; промежуточные сбои при чистом итоге попадают во вложение «Итог очистки». Повторное закрытие не отправляет запросы повторно.

E2E требует пустого исходного и итогового списка и разрешения `-De2e.authorized=true`. Флаг подтверждает разрешённый ограниченный прогон; область видимости списка и изоляцию он не доказывает. Появление чужого игрока может привести к падению проверки, но не разрешает его удаление.

## Allure и диагностика

Allure получает нативные результаты Jupiter, явные шаги и HTTP-вложения через Runtime API без AspectJ. `SafeAllureFilter`, `ReportingFeignClient` и `HttpDiagnostics` передают только обработанную диагностическую копию; тест проверяет исходный ответ.

`ReportSanitizer` скрывает пароли, семейства полей token/secret/apiKey, заголовки авторизации, cookie, JWT, email (в том числе `createBy`) и отражения известных секретов. Секретные DTO имеют безопасный `toString`; ошибки не раскрывают исходное чувствительное сообщение. Небезопасно разбираемое JSON-тело или слишком большое тело не прикладывается.

Результаты API находятся в `target/allure-results/api`, self — в `target/allure-results/self`. Отчёт по умолчанию строится только по API; профиль `self-report` выбирает локальные проверки.

Локальные самопроверки — быстрые модульные тесты оракулов, журнала владения, очистки, маскирования и транспорта на искусственных данных и loopback-ответчиках. Контрпримеры оракулов задаются прямо в данных: удаление соседа вместо цели, чужой профиль, сохранённая отклонённая запись, раскрытый идентификатор. Отдельная JVM используется только там, где нужен реальный жизненный цикл Jupiter и файлы Allure: XFAIL и маскирование отрицательной авторизации. Намеренные ошибки этих проверок не смешиваются с основным отчётом. Сами API-тесты против подставного сервера не запускаются: локальная проверка оснастки и результат живого API — разные виды доказательств.

## Принципы развития

DRY применяется к общему смыслу: маршрутам, транспорту, кодеку, владению и диагностике. Повторение независимых ожиданий допустимо, если оно сохраняет ясность проверки. KISS означает небольшие компоненты с явной ответственностью; общий `BaseApiTest` и универсальный исполнитель сценариев не вводятся.

Новый случай начинается с требования, риска, предусловий, классов входов и наблюдаемых последствий. После изменения выполняются подходящие проверки и независимое ревью читаемости, оракулов и надёжности. Замечание закрывается адресным контрпримером, а не только зелёным общим прогоном.
