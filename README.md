# Slotegrator — автоматизация Players API

Java-проект для задания из шести шагов с 12 игроками и независимых проверок пяти API-операций. Каждый тест готовит собственные данные и очищает их через JUnit lifecycle. Требования отделены от наблюдаемого поведения стенда.

## Результат проверки

Контрольный прогон на стенде — **9 октября 2026, 19:02–19:07 (Europe/Istanbul)**, строгий режим, `./mvnw -Papi-tests -De2e.authorized=true clean verify`:

| Набор | Результат |
|---|---|
| Локальная оснастка | **207 PASS**, без ошибок, около 10 секунд |
| API: 50 integration + 7 contract + 1 E2E | **26 PASS / 32 FAIL**, сборка завершается ошибкой |
| Целевой E2E | **Все шесть шагов задания пройдены**: 12 игроков созданы, их профили и список проверены, сортировка совпала с эталоном, каждый игрок удалён адресно, итоговый список пуст. Тест падает на седьмом шаге — итоговой сверке с заданием и OpenAPI |

Итоговая сверка E2E перечисляет отклонения ответов: вход 201 вместо 200 ([BUG-001](docs/bugs/BUG-001.md)), ответ входа не TokenDTO ([BUG-002](docs/bugs/BUG-002.md)), строковый ID вместо целочисленного в 36 ответах создания, профиля и удаления ([BUG-003](docs/bugs/BUG-003.md)), профиль 201 вместо 200 в 12 ответах ([BUG-004](docs/bugs/BUG-004.md)).

Все 32 падения — воспроизведения описанных расхождений: 22 случая создания (BUG-008), два Basic (BUG-006), семь контрактных проверок и итоговая сверка E2E. Это не 32 разных дефекта. BUG-004 остаётся конфликтом задания и OpenAPI, BUG-007 — вопросом о приоритете валидации; его семь проверок отказа без токена прошли.

Во всём API-наборе создано 94 игрока и удалены все 94 подтверждённых ID; итоговое чтение вернуло 200 и пустой список. Ошибок подготовки и очистки нет. Self и API проверены раздельно; во вложениях не обнаружены значения реквизитов из локальной конфигурации. Версия сборки backend неизвестна.

Самопроверки оснастки модульные: оракулы проверены контрпримерами в данных (удаление соседа вместо цели, чужой профиль, сохранённая отклонённая запись, раскрытый идентификатор), журнал очистки — на сбоях чтения и удаления. Это проверка качества оснастки, а не результат стенда.

E2E проходит все шесть шагов: нарушение полей, сортировки или адресного удаления прерывает сценарий, а отклонения кодов задания и схем ответов отмечаются в своих шагах и проваливают тест на итоговой сверке со списком отклонений и номерами багов. Подготовка остальных тестов совместима как с опубликованной, так и с явно описанной наблюдаемой формой API.

## Подготовка

Установите JDK 25 и задайте `JAVA_HOME`. Для Homebrew на macOS:

```bash
export JAVA_HOME="$(brew --prefix openjdk@25)/libexec/openjdk.jdk/Contents/Home"
export PATH="$JAVA_HOME/bin:$PATH"
./mvnw -version
cp config.example.properties config.local.properties
```

В Windows cmd используйте `mvnw.cmd` вместо `./mvnw` и `copy config.example.properties config.local.properties` для копирования. В Java Properties обратный слэш в пути экранируется двойным слэшем.

Для стенда заполните `BASIC_AUTH_USERNAME`, `BASIC_AUTH_PASSWORD`, `TESTER_EMAIL`, `TESTER_PASSWORD`, `CURRENCY_CODE`; в образце выбрана USD. При необходимости измените `BASE_URL` и таймауты. Переменные окружения имеют приоритет над файлом, включая пустые значения. Другой файл выбирается через `-Dapi.config.file=...`; `.env` автоматически не загружается.

Локальные реквизиты, `target/` и `work/` исключены из Git. Секреты не передавайте аргументами команд. HTTP-вложения маскируют пароли, токены, ключи, cookie и email, включая `createBy`; сами проверки получают исходный ответ.

## Запуск

Локальная проверка без реквизитов и без обращения к стенду:

```bash
./mvnw clean verify
```

API требует профиля `api-tests`. Surefire дополнительно исключает тег `api`: выбор `-Dtest=...IT` не открывает доступ к стенду. Пустой выбранный набор завершает сборку ошибкой.

```bash
./mvnw -Papi-tests "-Dapi.test.tags=api & e2e" -De2e.authorized=true clean verify
./mvnw -Papi-tests -De2e.authorized=true clean verify
./mvnw -Papi-tests "-Dapi.test.tags=api & smoke" clean verify
./mvnw -Papi-tests "-Dapi.test.tags=api & integration" clean verify
./mvnw -Papi-tests "-Dapi.test.tags=api & contract" clean verify
./mvnw -Papi-tests "-Dapi.test.tags=api & AUTH-04" clean verify
```

Двойные кавычки вокруг всего аргумента с тегами подходят также для Windows cmd после замены имени Wrapper. `clean` удаляет результаты предыдущего запуска.

Для E2E необходим `-De2e.authorized=true`: явное разрешение ограниченного прогона. Без него тест останавливается до HTTP. Флаг не доказывает изоляцию стенда. Сценарий требует пустого начального списка, создаёт не более 12 игроков, удаляет только подтверждённые собственные ID и проверяет полностью пустой итог. Чужие записи не удаляются даже при падении.

| Документ | Содержание |

| [BUG-004](docs/bugs/BUG-004.md) | Конфликт требований: профиль 200 в задании и 201 в OpenAPI |
| [BUG-005](docs/bugs/BUG-005.md) | Документация описывает объект вместо списка |
| [BUG-006](docs/bugs/BUG-006.md) | Нарушение безопасности: объявленная Basic-проверка не применяется |
| [BUG-007](docs/bugs/BUG-007.md) | Вопрос к требованиям: приоритет валидации и отказа входа, 400/401 |
| [BUG-008](docs/bugs/BUG-008.md) | Некорректный PlayerRequestDTO сохраняется с 201 |

**По умолчанию нарушения дают FAIL и сборка не проходит.** При точном воспроизведении известной причины аннотация прикладывает в Allure ссылку и Markdown бага; посторонний сбой ссылку не получает. Если отмеченный тест прошёл, он остаётся успешным с меткой `NOT_REPRODUCED`: отметку пора перепроверить. Для отдельного разбора известных расхождений:

```bash
./mvnw -Papi-tests "-Dapi.test.tags=api & (contract | integration)" -Dxfail.enabled=true clean verify
```

Этот режим выполняет тест и teardown. Только точная типизированная причина известного дефекта становится **XFAIL**, представленным как `skipped` с явной меткой. Ошибки подготовки, сети, очистки и новые причины остаются падениями; **XPASS** также проваливает сборку. Тексты ошибок и имена методов в стеке не используются для распознавания. BUG-007 не имеет XFAIL. Целевой E2E не использует XFAIL: известные расхождения в нём остаются падением итоговой сверки.

## Allure и форматирование

```bash
./mvnw allure:report
./mvnw allure:serve
./mvnw -Pself-report allure:report
./mvnw spotless:apply
```

API-результаты находятся в `target/allure-results/api`, отчёт — в `target/allure-report/api`. Self-результаты — в `target/allure-results/self`, отчёт с профилем `self-report` — в `target/allure-report/self`. Они не суммируются в один показатель. Вложенный Markdown позволяет прочитать описание бага вне репозитория. Намеренно ошибочные локальные фикстуры пишут результаты отдельно.

Фаза `validate` проверяет форматирование без изменения исходников; `spotless:apply` применяет общий стиль.
